# 🚀 Explore With Me (Миграция на Spring Cloud и Микросервисы)

Платформа **Explore With Me** помогает пользователям организовывать досуг: публиковать анонсы интересных мероприятий, управлять заявками на участие, оставлять комментарии и находить компанию для совместного посещения событий.

В рамках второго этапа дипломного проекта монолитное приложение было успешно переведено на микросервисную архитектуру. Основная цель — повысить отказоустойчивость, обеспечить независимое масштабирование сервисов и внедрить механизмы самовосстановления распределенной системы при сбоях.

---

## 🏗️ Архитектура и структура модулей

Проект реорганизован и разделен на изолированные модули, сгруппированные по их назначению:

### ⚙️ Инфраструктурный слой (`infra`)
Группирующий модуль для служебных сервисов экосистемы Spring Cloud:
* **discovery-server (Spring Cloud Eureka)** — центральный реестр, в котором динамически регистрируются все запущенные микросервисы для последующего обнаружения друг друга.
* **config-server (Spring Cloud Config)** — единый центр управления конфигурационными файлами (`.yml`), откуда сервисы запрашивают настройки при старте.
* **gateway-server (Spring Cloud Gateway)** — центральный API-шлюз, принимающий все внешние запросы клиентов на порту `8080` и маршрутизирующий их к соответствующим микросервисам.

### 💼 Слой бизнес-логики (`core`)
Каждая бизнес-сущность вынесена в отдельный автономный микросервис со своей базой данных и зоной ответственности:

| Сервис | Назначение |
| :--- | :--- |
| **user-service** | Администрирование пользователей и управление профилями. |
| **event-service** | Ядро управления событиями: создание, модерация, публикация, обновление и поиск. |
| **category-service** | Ведение и категоризация типов мероприятий. |
| **request-service** | Обработка и модерация заявок пользователей на участие в событиях. |
| **compilation-service** | Управление тематическими подборками событий. |
| **comment-service** | Изолированный функционал для публикации и модерации комментариев к событиям. |
| **common** | Общий модуль, содержащий разделяемые DTO, кастомные исключения и глобальный обработчик ошибок (`ErrorHandler`). |

### 📊 Сервис статистики (`stats-service`)
Изолированный слой для аналитики просмотров:
* **stats-server** — сбор, агрегация и предоставление статистики переходов по эндпоинтам.
* **stats-client** — клиентский модуль, подключаемый к бизнес-сервисам для отправки метрик.
* **stats-dto** — общие объекты передачи данных для слоя статистики.

## 🛡️ Отказоустойчивость и межсервисное взаимодействие

### 🔌 Внутреннее API и OpenFeign
Связь между микросервисами бизнес-логики осуществляется по протоколу HTTP с помощью **Spring Cloud OpenFeign**. Вместо жестко прописанных URL-адресов сервисы находят друг друга динамически через службы `DiscoveryClient` и реестр Eureka.

> 💡 **Масштабируемость:** Бизнес-сервисы запускаются на случайных свободных портах (`server.port=0`), что исключает конфликты при горизонтальном масштабировании.

<details>
<summary><b>🔍 Посмотреть основные точки интеграции через Feign-клиенты</b></summary>

* **Взаимодействие с `user-service`:** другие сервисы (например, `event-service` и `comment-service`) запрашивают данные автора или проверяют существование пользователя (`GET /internal/users/{userId}`).
* **Взаимодействие с `category-service`:** проверка валидности категории при привязке к событию (`GET /internal/categories/{catId}`).
* **Взаимодействие с `request-service`:** подсчет текущего количества одобренных заявок на событие для контроля лимита участников (`GET /internal/requests/event/{eventId}/count`).
</details>

### 💥 Защита от сбоев (Circuit Breaker & Fallback)
Для предотвращения эффекта «домино» (когда падение одного сервиса ломает всю систему) внедрены паттерны отказоустойчивости с помощью **Resilience4j**:

1.  **Паттерн Fallback (Заглушки):** Если вызываемый микросервис (например, сервис заявок или пользователей) недоступен или отвечает с ошибкой `5xx`, Feign-клиент перехватывает сбой с помощью `FallbackFactory` и возвращает безопасное дефолтное значение (например, `0` для счетчиков или объект-заглушку `Unknown User`), позволяя основному потоку успешно завершить обработку запроса.
2.  **Политика повторов (Retry):** Для сглаживания временных сетевых колебаний настроен механизм автоматических повторных попыток. При возникновении `IOException` или `503 Service Unavailable` клиент совершает до 3 попыток вызова с паузой.

#### Базовые параметры отказоустойчивости в Config Server:
```properties
resilience4j.circuitbreaker.instances.default.sliding-window-size=10
resilience4j.circuitbreaker.instances.default.failure-rate-threshold=50
resilience4j.circuitbreaker.instances.default.wait-duration-in-open-state=10s

resilience4j.retry.instances.default.max-attempts=3
resilience4j.retry.instances.default.wait-duration=1s
```

## 🚦 Порядок локального запуска

Для корректной инициализации всех связей рекомендуется запускать модули в следующей последовательности:

1.  **discovery-server** — поднимает общую карту сети (порт `8761`).
2.  **config-server** — разворачивает службу конфигураций (случайный порт, регистрируется в Eureka).
3.  **stats-server** & **ewm-service** — загружают настройки из Config Server и регистрируют свои адреса в Eureka.
4.  **gateway-server** — активирует шлюз (порт `8080`), подтягивает маршруты и начинает проксировать внешний трафик к основному приложению.
